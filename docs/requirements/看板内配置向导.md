## 一、总体目标

给**不懂技术的新用户**解决「装好之后不知道怎么配置」：不经过控制台窗口，在浏览器里打开看板就能完成首次配置——
选要监控的平台、填密钥、由页面把配置写进本机文件、立刻看到「到底成没成」，并知道怎么让它自动运行。

一句话验收：**一个不懂技术的用户，只用看板页面（加至多一次双击静默脚本）就能从「没有数据」走到「平台采到数据、以后自动采」。**

范围：

- 只服务「本机这一个项目目录」；不做多项目 / 多文件夹管理。
- 不引入服务端、不引入第三方依赖（零依赖是硬约束）。
- 不删控制台向导（`首次配置.bat`）——保留为兜底路径。

## 二、功能用户故事

### US-1 打开看板就知道怎么开始

**作为一个第一次打开看板的用户，我想要在「还没有数据」的开屏上看到一句大白话说明和一个「开始配置」按钮，以便不用翻 README 就知道下一步做什么。**

范围边界：不自动打开配置界面（必须用户点击）；不在页面加载时自动触发任何后台动作。

### US-2 选要监控的平台，并按本机探测结果给建议

**作为一个不知道该开哪几个平台的用户，我想要向导里列出三家平台、显示本机已经具备哪些能力（Codex 登录、已有密钥）并据此给建议，以便只开我要用的那几家。**

范围边界：探测只读「有没有、从哪来、多长」，不读密钥明文、不联网、不修改任何文件；探测不可用（系统侧还没启用）时允许手动选。

### US-3 在向导里准备密钥（向导不接触密钥值）

**作为一个不懂技术的用户，我想要在向导里看到每家平台「有没有密钥、从哪来」以及缺的那家去哪儿补，以便不用自己创建和编辑 JSON 文件，也不用把密钥交给看板。**

范围边界：向导不接收、不保存、不显示密钥值（密钥只由 ThinCoder 配置 / `secrets.json` / 环境变量维护）；Codex 一律不问密钥（它的凭据来自登录文件）；
没找到密钥时给 ThinCoder 安装引导与「重新检查」，不阻塞下一步。

### US-4 一次点击把平台开关写进本机文件（不碰密钥文件）

**作为一个用户，我想要点一次「保存」后，由页面把平台开关写进本项目目录的 `config.json`（密钥文件一字不动、选错文件夹会被拒绝且不产生任何写入），以便不用手动改文件。**

范围边界：只写平台开关（3 个布尔），不写密钥、不碰阈值与路径等其它配置；绝不写所选文件夹以外的任何文件。

### US-5 保存后立刻知道「成没成」

**作为一个想知道结果的人，我想要保存后能触发一次采集并在同一页看到每个平台的结果，等待期间有明确提示、超时了有解释与下一步，以便不用跑命令行确认。**

范围边界：采集必须由用户点击触发；单次等待设上限（超时给下一步，不无限转圈）。

### US-6 明确「怎么让它自动运行」

**作为一个不想每天手动采集的用户，我想要在看板里看到「自动采集：已开启 / 未开启」以及开启办法，以便配置完就真的不用管它。**

范围边界：页面不自己实现调度（仍由 Windows 计划任务负责）；开启动作幂等，重复执行不产生额外副作用。

### US-7 浏览器不支持时给兜底，不让按钮点了没反应

**作为一个用 Firefox 或旧浏览器的用户，我想要向导明确告诉我「这个浏览器不能在页面里直接写文件」，并给出可照做的替代路径，而不是按钮点了没动静。**

范围边界：不为此引入 polyfill / 第三方库 / 服务端；兜底路径不写任何文件。

### US-8 回访与再配置

**作为一个已经配置过的用户，我想要再次打开向导时看到当前状态、只补或只改需要的那部分（幂等、不重复问），以便后续维护不用重走全程。**

范围边界：不提供「清空配置」；不做配置版本历史。

### US-9 文案与入口收敛（不再有「必须双击 .bat」）

**作为一个用户，我想要看板上不再出现「必须双击 .bat 才能配置」这类过时指引，配置入口收敛为「向导为主、控制台向导与记事本编辑为兜底」，以便不被两条互相矛盾的路搞晕。**

范围边界：不删控制台向导、不删「编辑密钥文件」入口；平台开关按钮的既有通道不变。

## 三、非功能标准

### NFR-1 安全（密钥生命周期，硬要求）

**看板内的配置向导不接触密钥值**（2026-09-17 用户裁定）：页面没有密钥输入框，也不读写 `secrets.json`。
密钥值只允许出现在三处，而且这三处都由 ThinCoder 或用户自行维护：

1. `secrets.json` 文件内容（老用户与手动维护路径）；
2. ThinCoder 配置里的 API Key（**推荐路径：密钥只存一处**）；
3. 环境变量 `DEEPSEEK_API_KEY` / `GLM_API_KEY`。

向导只读「有没有、从哪来」两个标签（`lib/common.mjs` 的 `resolveApiKey` 给出的 `found` / `source`），永不读值。
禁止出现于：导航 URL / iframe 地址、localStorage / sessionStorage / IndexedDB、DOM 序列化、控制台输出、
`data/protocol.log`、`data/state.json`、`dashboard-data.js`、任何日志。

**度量方式**：无头浏览器插桩断言（设计档 A6：向导全程对密钥文件零读零写 + 存储 / iframe / console / DOM 零命中）；发布闸门密文审计（`node release/publish.mjs --dry`）。

### NFR-2 兼容性（浏览器能力差异）

目标环境：Windows 10 / 11 上的 Chromium 系浏览器（Edge / Chrome）。
能力检测点：`showDirectoryPicker` 存在、且选中后拿到的句柄具备 `createWritable`。不支持时给兜底面板（见 US-7）。

**度量方式**：桩函数测试（设计档 A2）+ 人工用 Firefox 打开核对（设计档「人工验收步骤」）。

### NFR-3 可用性（小白可独立完成）

全程不出现 JSON / schema / HTTP 状态码 / 命令行这类黑话；每一步都告诉用户「现在在干什么、下一步在哪儿」；
任何失败都有可照做的下一步；首次配置（含一次试采）能在 3 分钟内完成。用户可见提示一律中文，且完成时必有结果提示——
含静默引导脚本（`启用自动采集.vbs`）的结果提示（2026-09-15 用户裁定「必须中文、必须有」；落地见设计档 2.2.13 / A17）。

**度量方式**：人工走查清单（设计档「人工验收步骤」，含步骤 5 的中文弹框核对）+ 文案审查（对照黑话词表）+ 中文提示载荷机判（设计档 A17 / T39）。

### NFR-4 性能

1. 体量：**不因新增代码而削减功能与验收**（原「≤ 30KB」上限已于 2026-09-16 由用户解除）；
2. 打开向导 < 200ms（不含网络与探测）；
3. 探测往返 ≤ 10s，超时即降级为手动模式；
4. 试采等待 ≤ 90s，超时给下一步；
5. 对既有页面首屏无影响（新增逻辑只在向导 / 引导路径上执行）。

**度量方式**：测试脚本计时 + 文件体积断言（设计档 A13）。

### NFR-5 可维护与纪律

1. 零依赖不变（不新增第三方依赖、不新增服务端 / 监听端口）；
2. `.vbs` 保持纯 ASCII（Windows 脚本宿主按 ANSI 代码页读取，中文注释会破坏解析）；
3. 控制台向导保持可用且行为不变；
4. 页面写入与既有协议写入（平台开关白名单）语义同源：同一组键、同一合并语义；
5. 新增探测脚本不打印、不落盘任何密钥值（沿用既有「只报来源与长度」纪律）。

**度量方式**：A8 / A9 门禁 + A17（`.vbs` ASCII 与中文提示链路）+ 代码走查（设计档「多实现面与语义同源」一节）。
