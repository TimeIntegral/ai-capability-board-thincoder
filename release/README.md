# 发布管理

**这个目录负责"从本地到公开"的每一步**。目标是让"什么该公开"变成机械判断，而不是靠记性。

## 当前推荐入口

开发时保存本地提交即可，不代表公开发布。准备发布运行 `node release/prepare.mjs`：要求工作区干净，在独立 worktree 从 HEAD 测试并构建，输出到 `dist/candidate-<版本>-<提交>/`，包含安装包、便携包、校验清单及代码快照记录。候选版不自动上传，开发目录可继续修改。

公开发布时应将候选记录中的完整 commit 标为 `v<版本>`，不要把后来开发的 HEAD 当成候选版。日常版安装在安装程序默认目录，开发目录禁止注册后台任务和安装更新。

下面的 `publish.mjs` 是底层审计与打包工具；直接打包同样要求干净提交。推荐用 `prepare.mjs` 完成安装包构建。

## 底层工作流

```
你平时：随便改、随便提交（VERSION 不动）
要发布：① 改 VERSION + 在 CHANGELOG 顶部写一条 "## <新版本>"
        ② git add -A && git commit -m "release: v<版本>"     ← 先提交：标签必须落在已提交的内容上
        ③ node release/publish.mjs --dry      ← 预演：只看会拦下什么，不动任何东西
        ④ node release/publish.mjs --tag      ← 过闸：审计 → 版本 → 打包 → 打标签
        ↓
   ① 文件清单：git 将跟踪的全部文件（= 下一次 push 会公开的范围）
   ② 审计：命中密钥 / 个人信息 / 禁入路径 → 汇总 → 拒绝（exit 1）
   ③ 版本一致性：VERSION ↔ CHANGELOG 顶部 ↔ 代码里的版本常量 ↔ --version
   ③b 运行时：runtime/node.exe 必须在、且 SHA256 与 release/portable-node.json 一致
   ④ 打包：dist/<包名>-v<版本>.zip = 代码 + 便携 Node 运行时（dist/ 已 gitignore）
   ⑤ 打标签：git tag v<版本>（仅 --tag；要求工作区干净，标签才落在发布内容上）
   ⑥ 打印下一步：推送 / 上传，命令直接可抄
        ↓
   你确认后：git push（代码 + --tags）+ 上传 zip 到 GitHub Releases
```

②③③b 会全部跑完再汇总报错（不会卡在第一个问题上，省得来回好几趟），
但只要有一步不过就**一步都不往下走**：不打包、不打标签。

## 用法与退出码

| 命令 | 作用 |
|---|---|
| `node release/publish.mjs --dry` | 只审计 + 查版本 + 查运行时，不打包、不打标签 |
| `node release/publish.mjs` | 全流程：审计 → 版本 → 打包（不打标签） |
| `node release/publish.mjs --tag` | 同上，最后 `git tag v<版本>`（工作区必须干净，否则拒绝） |
| `node release/publish.mjs --version 1.2.3` | 声明"这次发的是 1.2.3"，与 `VERSION` 不一致就拒绝 |
| `node release/publish.mjs --no-runtime` | 本次发布包不带便携 Node 运行时（没装 Node 的用户无法"解压即用"） |
| `node release/publish.mjs --help` | 帮助 |

**退出码**：`0` = 过闸；`1` = 被拒绝（审计命中 / 版本不一致 / 运行时缺失或对不上 / 工作区不干净 /
标签重名 / 参数不认 / 仓库还没有提交）。参数写错、规则表写坏、标签重名一律报错停下 —— **拿不准就拒绝，绝不放行**。

## 设计原则

1. **默认拒绝** —— 审计不通过就不发布，宁可误报也不放过
2. **单一版本源** —— `VERSION` 文件是唯一的版本号：CHANGELOG 顶部与代码常量必须与它一致；
   `--version` 只是"声明"，不会替你改 `VERSION`（要发新版本先改 `VERSION` 文件）
3. **本地领先是常态** —— GitHub 上永远是"最后一次发布的状态"，本地随便领先
4. **私有区隔离** —— `private/`、`data/`、`backups/`、`config.json`、`secrets.json` 物理隔离；
   它们连"被跟踪"的资格都没有，所以根本进不了审计范围 —— 这本身就是一层保障
5. **审计范围 == 发布范围** —— 清单直接取自 git，所以"审计通过"就等于"下一次 push 的所有文件都过检"
6. **发布工具自己也不许破例** —— `release/` 目录下的文件同样要过闸门（唯一的例外见下）

## 文件

| 文件 | 作用 |
|---|---|
| `publish.mjs` | 主流程（审计 → 版本 → 运行时 → 打包 → 打标签 → 下一步） |
| `audit-rules.json` | 脱敏规则：密钥模式、个人信息清单、禁止路径、放行名单（`$豁免`） |
| `make-portable.mjs` | 下载并内置便携 Node 运行时（供一键安装用；校验和从官方取，二进制可走国内镜像） |
| `portable-node.json` | 便携 Node 的来源记录（版本、镜像、官方 SHA256）—— 打包时用它核对运行时真伪 |

## 审计查什么

规则写在 `audit-rules.json`，每条都有 `id` / `描述` / `模式` / `严重级`，加词只需往下加一条。

| 类别 | 规则 id | 拦什么 |
|---|---|---|
| 密钥 | `secret-sk` | `sk-` 开头的 API 密钥 |
| | `secret-bearer` | 请求头里的 `Bearer` 令牌 |
| | `secret-assign` | `apiKey` / `token` / `secret` / `password` 后面跟着写死的字符串 |
| | `secret-jwt` | `eyJ` 开头的三段式 JWT |
| | `secret-long-random` | 32 位以上的疑似随机串（base64 / 十六进制密钥） |
| 个人信息 | `pi-user-name` | 本机用户名 |
| | `pi-project-root` | 本机项目根目录名 |
| | `pi-user-path` | 用户目录绝对路径（盘符 + `Users` + 用户名） |
| | `pi-drive-path` / `pi-drive-path-fwd` | 盘符绝对路径（反斜杠写法 / 正斜杠写法，如 `file:///?:/…`） |
| | `pi-email` | 邮箱地址 |
| | `pi-real-projects` | 真实项目名清单（发现一个加一个） |
| 禁入文件 | `forbid-*` | `config.json` / `secrets.json` / `dashboard-data.js` / `data/` / `backups/` / `private/` / `.thincoder/` / `.env` / `*.zip` / `*.log`（万一被 force-add） |

命中输出形如 `文件:行号  类别·描述  「片段…」` —— 片段只显示前 12 个字符（脱敏），
末尾按规则给汇总（哪条规则命中几次）。

### 写规则时的两条硬要求

- **量词必须有上限**：写 `{1,64}`，不要写 `+`／`*`。无上限的量词碰上一行超长文本
  （压缩过的 js、大 JSON）会把扫描拖成平方复杂度，闸门直接卡死 —— 这是实测踩到的坑。
- **多行匹配不做**：逐行扫，正则里别指望跨行的 `\n`。

### 认出误报之后怎么办

- **整条规则错了** → 删掉那条规则。
- **只有某一处是误报**（例如官方下载的校验和）→ 在 `audit-rules.json` 的 `$豁免` 里加一条：
  必须写清 **文件**（正则，带 `^$` 卡死）、**规则**（真实存在的 `id`）、**说明**（为什么它不是秘密），
  可选 **命中** 再卡一层形状。放行结果会在审计输出里**大声打印**出来，不允许静默放行。

### 唯一自带豁免的文件

`release/audit-rules.json` 必须**原样列出**个人信息词表（用户名、真实项目名…），否则它会拦下自己。
所以对它只跳过「个人信息」这一类；**密钥类照常扫** —— 规则表里本来就不该出现真密钥。

## 发布包里有什么

`dist/<包名>-v<版本>.zip` 解压后是一个一级目录 `<包名>-v<版本>/`，里面：

- **审计过的代码** —— 就是 ① 那份清单，审计什么就发布什么（一个不多、一个不少）；
- **便携 Node 运行时** `runtime/node.exe` —— 给没装 Node 的用户"解压即用"
  （`快捷操作\安装定时任务.bat`、`快捷操作\立即采集一次.vbs` 都优先用它）。
  它 80MB、被 `.gitignore` 排除，所以**不在逐行审计范围**里 —— 换来的是
  **SHA256 核对**：必须与 `release/portable-node.json` 里记录的官方校验和一致，否则拒绝打包。
  确实要发纯代码包时用 `--no-runtime`（输出里会明说"没装 Node 的用户无法直接用"）。

打包后用 `--dry` 之外的任何方式改动过工作区，请重跑一次；`--tag` 会拒绝在脏工作区上打标签。

## 为什么打包不用 PowerShell 的 Compress-Archive

`程序/tools/backup.mjs`（备份）用的是 `Compress-Archive`，发布包**故意不用**它：

1. 本仓库半数以上的文件路径含中文（`快捷操作\安装定时任务.bat`、`程序\运行协议.vbs` 等）。Windows PowerShell 5.1 的
   `Compress-Archive` 不写 zip 的「UTF-8 名称」标志位，换台机器、换个解压工具就可能全是乱码。
2. 本项目目录名本身含中文，外部工具的代码页/区域设置正是最容易翻车的地方
   （同类坑已踩过：Node 的 `fs.cpSync` 在中文路径下会原生崩溃）。
3. 自己写能保证：名称一律 UTF-8 + 置通用标志位 11，输出字节可复现，没有外部进程。

实现只用 `node:zlib`（`deflateRawSync` 压缩 + `crc32` 校验），依然是零依赖、单进程；
写完后**自己再读一遍**（走中央目录 → 局部头 → 解压 → 比对大小与 CRC），坏了就不发布。
实测：PowerShell `Expand-Archive` 与 Windows 自带的 `tar` 都能解开，中文名原样还原，运行时字节一致。

## 已知边界

- **二进制不扫内容**（图标、node.exe 等）：只列出来提醒你它进了发布包，不逐字节找密钥；
  运行时的真实性由 SHA256 记录兜底，其余二进制靠"它是从哪来的"。
- **单个文件超过 8MB 直接拒绝**，不是跳过 —— 大体积发布物不该进 git（便携运行时就是这么处理的）。
- **长随机串要求前 64 个字符里同时有字母和数字**：纯数字的长串（时间戳、大整数）不拦。
- **真实用量数字不单独设规则**：它们只住在 `data/`、`dashboard-data.js`、`config.json` 里，
  由「禁入文件」规则兜住 —— 不重复设一条注定误报的规则。
- **`*.zip` / `*.log` 被列为禁入**：正常路径进不来（gitignore 挡着），这是防 force-add 的兜底。
- **便携运行时的来源只核到"下载时记录的官方校验和"**：闸门不联网复验 nodejs.org，
  记录文件本身被改过它认不出来（但这属于"你自己改自己的仓库"）。
